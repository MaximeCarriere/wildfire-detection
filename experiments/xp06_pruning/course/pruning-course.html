build → shrink → measure

Pruning removes parts of a neural network to make it smaller and faster. This is a working course in every way you can do that, tested on a smoke-and-fire detector running on a fanless $249 board — including the versions that failed.

A detector that must run on a pole in a forest

The job is spotting smoke and fire early enough to matter, on hardware with no fan and no internet. Fifteen watts, eight gigabytes, no cloud.

That budget is what makes compression interesting. A model that is 5% more accurate but three times slower is not better here, it is unusable. So every technique below is judged against one measured line: the unpruned detector, fed 512-pixel images, compiled to a real engine. 0.7776 mAP50 at 474 images per second. Anything that does not beat that has lost.

the running joke

The most effective compression so far was feeding the network smaller pictures. Not pruning, not quantisation. Just 512 pixels instead of 640. The cheap knob is beating the clever ones, and a fair course says so before it teaches you the clever ones.

What the numbers mean

mAP50 is the standard detection score: did the box the model drew land on the thing that is actually there. 1.0 is perfect, 0.0 is useless.

One number is never enough. A wildfire system exists to catch fires early, which means catching them while the smoke is still a smudge on the horizon. So accuracy is always split by size: small plumes are under 1% of the frame, tiny plumes under 0.1% — roughly a 20×20 pixel patch. A model can hold its headline score while going quietly blind to exactly the case it was built for, and the only way to see that is to measure it separately.

Every pruning method is four decisions

The literature looks like dozens of competing techniques. It is one problem with four independent choices, and almost every named method is a particular combination of them.

Formally: keep the network as accurate as possible while holding no more than N non-zero weights. Everything below answers which weights, in what pattern, how many per layer, and what training happens afterwards.

That is one cell of a four-dimensional space, and the conclusion drawn from it — "pruning loses" — is only as broad as the cell it came from.

Granularity → the shape of the hole you leave

A network's weights are grids of numbers. Pruning sets some to zero. This axis asks what shape the zeros make, and that decides whether any hardware can exploit them.

One trade-off governs everything: the more freely you choose what to drop, the more you can drop, because you can always find the genuinely useless weights. But scattered zeros do not make a matrix smaller, they make it a matrix with holes, and a GPU multiplies it at exactly the same speed. Regular patterns delete less and actually run faster.

The two that matter here

Channel pruning is the only one that makes a network genuinely smaller on ordinary hardware. Remove a channel and the matrix loses a whole dimension: fewer rows, fewer columns, less arithmetic, no special kernel required. That is what has been tested so far, and that is why.

2:4 sparsity is the interesting one. The rule is rigid — of every four neighbouring weights exactly two must be zero — and the rigidity is the point, because Ampere GPUs have circuitry that skips those zeros for roughly double the throughput. It is 50% sparsity with silicon behind it, and NVIDIA's published table shows a detector, SSD-RN50, going 24.8 → 24.8 box AP on COCO: no measurable loss. The target board is Ampere-class, so the path exists. Whether it delivers on this particular chip is a measurement, not a datasheet reading.

Criterion → deciding what is expendable

Something has to go. Which? The principle is easy to state and hard to apply: the less important the thing you delete, the less the network notices.

Each criterion below is a different theory of "important", and they genuinely disagree. Run them on the same layer and watch different channels get selected.

Why "random" is on that list

It looks like a joke entry and it is the most important control in the study. Every criterion above will produce a number. Without random next to them you cannot tell whether a criterion is smart, or whether any cut of that size followed by the same retraining lands in the same place. A leaderboard without a control says which method won. A leaderboard with one says whether winning meant anything.

A criterion that does not transfer

APoZ ranks channels by how often they output exact zeros — a channel that is almost always zero is doing nothing. It was designed for ReLU networks, which produce exact zeros constantly. This detector uses SiLU, which almost never outputs exactly zero, so literal APoZ would rank every channel as equally busy and decide nothing. The honest move is to adapt it to average activation size and label it an adaptation. Reporting that a textbook method does not transfer, and why, is worth more than quietly substituting a different one and reporting a number.

the mechanism

The collapse is not gradual because the confidence head fails first. The part of the network scoring "how sure am I something is here" falls from 0.72 to 0.0045 by the 5% cut. The model is still finding smoke internally and drawing boxes around it — it has simply stopped believing any of them, so nothing survives the threshold and the score reads zero.

This is why retraining is not a finishing touch in this project, it is the experiment. An accuracy-versus-sparsity curve without retraining, which is how pruning is usually illustrated, would be a row of zeros.

And when you do retrain, it still loses

Two ways of removing 25% of the channels, each given 12 epochs of recovery, each compiled to a real engine so the speed numbers are honest:

Three findings come out of that, and the third is the one worth chasing.

  1. Neither version beats doing nothing. One-shot gives up 4.8 accuracy points and runs 20% slower.
  2. Removing arithmetic is not gaining speed. Cutting 88.9% of the multiply-adds bought 1.7× the throughput, not the ~9× the arithmetic implies. Pruned layers end up with awkward channel counts — 47 instead of 64 — and GPU kernels are built for neat tile sizes.
  3. The bigger pruned model was the faster one. Iterative kept more parameters (4.51 M vs 4.24 M) and ran substantially faster (450 vs 381 img/s). If that is real, how you prune matters more for speed than how much.
a confound, stated plainly

Both arms got 12 epochs. But the iterative model's final shape existed for only the last 4 of them, while one-shot trained all 12 in its final shape. Equal total budget is not equal recovery budget, so part of iterative's deficit may be nothing more interesting than a shorter run. Until that is fixed the comparison is not a clean result — which is what experiment 07 is for.

Eight experiments, ordered by what they teach per hour

Each isolates a different axis. The numbering is not decoration — it is the run order, because early results feed later ones.

One constraint shapes all of them. A compiled engine only runs on the GPU architecture it was built for, and a speed reading from a desktop RTX 3090 says nothing about a 15-watt board. So the desktop makes weights and screens accuracy; the board produces every number about speed, power and memory. Two experiments below can only be finished on the board, and they are marked.

01 · sensitivityrunning

Which layers can this detector afford to lose?

Prune one layer, measure, put it back, move on. 57 layers × 5 severities.

The output is a map of where damage is cheap and where it is fatal. This goes first because the pruning done so far used one global threshold across the whole network, which means it had no such map and was free to spend its budget in the worst possible place. That would explain a 2% cut costing 9 accuracy points.

The first cells are already suggestive: halving the network's first convolution destroys 84% of the accuracy and saves 0.16% of the parameters. A terrible trade, and a blind threshold is free to make it.

02 · criterionqueued

Does the choice of importance measure matter, and does any of it beat random?

Fix the amount at 25%, change only the rule for choosing victims, run all eight.

L2, L1, BN scale, Taylor, Hessian, FPGM, LAMP and random. Measure raw damage first because it is cheap, then pay for recovery training on the best few plus random.

One design change from the original plan. A 25% cut with no retraining already scores exactly zero, so at that ratio every criterion reads zero and the sweep ranks nothing. Damage is therefore also measured at 2% and 5%, where the model still produces usable output and the criteria separate. That the comparison has to be taken at 2% to exist at all is itself a statement about this detector.

03 · regularityneeds the board

Was the bigger-but-faster result really about neat channel counts?

Prune 25% four times with different rounding, retrain each identically, and measure. If regularity is the mechanism behind finding 3, heavier rounding should recover the missing speed at equal accuracy — a genuinely useful practical rule.

04 · 2:4 sparsityneeds the board

The one pattern with dedicated silicon behind it. Does it hold accuracy here?

Force two of every four neighbouring weights to zero, retrain, build a sparse engine.

Three things get reported separately and must not be blurred: whether accuracy held, whether the compiler actually chose sparse kernels, and what speed came out.

It is entirely possible accuracy holds and the speed-up never materialises on this chip. That is a publishable result and fits this project exactly, whose recurring theme is that hardware does not do what the arithmetic promises.

05 · fine-grained ceilingqueued

Is the collapse a capacity problem or a structure problem?

Delete individual weights anywhere, at 25 / 50 / 70 / 90%, retrain, measure accuracy only.

No speed-up is expected and none will be reported: scattered zeros have no matching kernels on this hardware, and saying so plainly is part of the result.

This is the experiment that licenses the strongest possible sentence. If the network survives 90% of its weights being deleted but dies at a 5% channel cut, then capacity was never the problem — structure was. That is a far more interesting and more accurate conclusion than "pruning does not work here", and right now there is no evidence to choose between them.

07 · the fair rerunqueued

Does iterative still lose once both arms get equal training in their final shape?

Fix the confound: equal epochs after the final cut. Then extend to 50 epochs.

The textbook says iterative should win — the standard figure has pruning alone failing past 50% sparsity, pruning with retraining holding to 80%, and iterative holding past 90%. The measurement here found the opposite ordering. That is a real disagreement with the literature and deserves a clean test rather than an excuse. If a longer budget flips it, the finding is about who can afford to prune, not about pruning.

Four traps that already cost real time

Measurement studies fail quietly. Each of these produced a plausible, publishable, wrong number before it was caught.

The library swapped the model

Asked to load yolov5s.pt, a popular library recognised the filename, silently downloaded its own 80-class model trained on general photographs, and returned that instead. It ran. It drew plausible boxes. It was measuring an entirely different network. Caught only by printing the class names, which should have read ['smoke', 'fire']. Every load now asserts that.

The training loop destroyed the model

A first attempt at recovery training took the unpruned model from 0.818 to 0.008 in a single epoch, and two published numbers had to be withdrawn. Three independent causes, each sufficient alone — most memorably a loss weight 40× too heavy, drowning out the very "is anything there?" signal that was collapsing. The standing rule: before believing any recovery number, retrain the unpruned model and check it comes back where it started. If that control fails, the session measured the training loop, not pruning.

Defaults are not neutral

A separate quantisation experiment lost 67% of its accuracy to one default setting, which decided the useful brightness range stopped at 45% and flattened the bright sky where faint smoke lives. It looked exactly like "this technique is bad for detection" — a tidy, quotable, wrong conclusion. It was one option, and changing it fixed the problem. When a pruning criterion produces a catastrophic result, suspect the setting before writing the conclusion.

The exported file was a stub

One export path silently wrote a 0.5 MB file for a model holding 4.24 M parameters, and failed no check because nothing checked. The export now asserts on file size.

the rule underneath all four

Every number goes through one measurement harness with a version stamp, and the figure generator refuses to draw a chart mixing versions. The data splits are frozen and checksummed, and training refuses to start if they do not match — which matters most when work moves to a second machine, because if the split changes there, test images leak into training and every published number silently becomes a score on an exam the model has already seen.
